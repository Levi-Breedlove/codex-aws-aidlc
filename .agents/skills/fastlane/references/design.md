# Design phase

Use for DESIGN-10 and Gate B. The Engine owns readiness, digests, and routing; this reference owns the design procedure.

## Architecture and AWS evidence

- Complete the whole-system application, security, data, failure, recovery, operations, cost, deployment, rollback, teardown, and verification design.
- For each material AWS question, identify current basis IDs, call `search_documentation`, choose the smallest relevant returned skill set, and call `retrieve_skill` with those exact identifiers. Follow the retrieved procedure and official references as needed. Record linked `AWS-DISC-*`, `AWS-EV-*`, findings, sources, times, and bindings, not raw instructions or transcripts. Generic connectors, memory, installed metadata, or challenger prose cannot replace those calls.
- Installing the plugin or selecting `@AWS-Core` proves availability only. Attribute use only after an observable current search-then-retrieve chain. External skill content is on-demand context, not repository source bytes or canonical state.
- Codex selects and coordinates the proposed product architecture. AWS Core supplies current AWS knowledge, decision guidance, procedures, and execution tools. Fastlane governs state, gates, authority, and evidence. The owner authorizes; IAM enforces; observed evidence proves what occurred.
- Apply compatibility before edits. Unchanged approved Design schemas 4–6 retain their existing bridges, and an exact approved Design 7 remains compatible only while its derived aggregate digest matches the stored Gate B envelope and no Design-8 record is mixed into it. New, unapproved, stale, partially migrated, or design-controlled work requires Design contract 9, new digests, and fresh Gate B. Design 9 requires Requirements 1.6. Preserve exact approved legacy pairs until a controlled migration; complete missing owner decisions without inventing facts, then renew the affected gates. A declared no-data project uses the exact no-dataset sentinel. Compatibility never permits broader authority, skipped validation, or a repeated owner question.

## Architecture selection and records

- Follow the current Adaptive Coverage Plan. `SELECT` compares at least two complete, credible, non-straw whole-system candidates. `AMEND` reconsiders every affected driver and alternative. `PRESERVE` requires proof that architecture, technology, trust, data, recovery, Region, and Harness boundaries are unchanged.
- Derive `DRV-*` from approved requirements. Evaluate hard constraints before preferences, include a secure managed-serverless baseline for greenfield work unless ineligible, never add a straw option, and never use arbitrary numerical scoring.
- Select one eligible `ARCH-*` recommendation. Record each rejected `CAND-*`, rationale, risk, mitigation, security/reliability impact, operational burden, cost effect, scaling breakpoint, migration path, revisit trigger, and validation method. Use `NO_VIABLE_ALTERNATIVE` only when at least two total candidates exist and exactly one is eligible.
- Map every approved requirement to the selected `ARCH-*`, declared interface/boundary/state records, applicable `EX-*`/`PROP-*`, and material `AWS-EV-*`. Undeclared IDs fail closed. Current AWS claims cite their `AWS-DISC-*` chain; detailed discovery evidence remains in VERIFY.
- When the owner asks for the architecture recommendation during Design, summarize the actual selected candidate and credible rejected alternative from the current canonical records. Include the material data lifecycle, failure/recovery, operations, cost, and exact validation boundaries, and link the current canonical decision and source locators. Do not substitute generic evidence language for the current source IDs or links.
- Complete interfaces and boundaries with concrete limits or explicit inapplicability, inward dependencies, server-side authorization, lifecycle/state triggers, and first-wave/spike records. Any spike is disposable, bounded by attempts, and has one executable exit check.
- Complete the error-handling record for validation, transient dependency, permanent dependency, concurrency conflict, and internal defect outcomes. Each row names a concrete example, bounded retry posture, safe user effect, operator signal, and recovery action; uncontrolled retry is invalid.
- Complete the AWS implementation approach during DESIGN-10, never during Gate A. Populate exactly one row in this canonical order: `Compute`, `API and edge`, `Identity`, `Data`, `Messaging`, `Observability`, `Deployment`, and `Secrets and encryption`. These are the material implementation concerns for the selected project design, not an exhaustive AWS product catalog; one row may name multiple services or mechanisms, and a non-applicable concern records a concrete reason instead of an invented service.
- Bind each row to the exact ordered `TECH-*` decisions that control it. Its mechanism reproduces those selections without inventing a second service choice, applicable decisions have current material `AWS-EV-*` evidence, and a wholly inapplicable concern stays explicitly inapplicable. Resolve service choices within Design when the evidence supports them; ask the owner only when an unresolved owner constraint or product tradeoff genuinely requires a decision.
- Record state applicability in canonical category order: `LIFECYCLE_RESOURCE`, `ASYNCHRONOUS_WORK`, `RETRY_OR_RESUME`, `APPROVAL_FLOW`, `MIGRATION_OR_CUTOVER`, `OTHER_MEANINGFUL_TRANSITION`. Applicable categories bind declared `STATE-*`; inapplicable categories bind `NONE` and a concrete reason. Interface and layer rows use explicit mapping, inward dependencies, server-side authorization, and measurable bounds or validated inapplicability.
- Complete the Change impact record for AMEND or PRESERVE. Bind changed, affected, and preserved IDs; uncertain impact uses `FULL_REVALIDATION`. It never overrides monotonic revisions or stale-gate rules.
- Map every current `DATASET-*` exactly once to its store/component, current implementation IDs, access and encryption enforcement, retention/deletion, backup/recovery, residency/migration, audit mechanism, and current validation IDs. Unknown, duplicate, missing, or out-of-order mappings fail closed.
- Record the intended environment and promotion graph using one root and only earlier declared promotion sources. Every row binds one immutable artifact boundary, configuration/secrets/data boundary, promotion evidence, rollback/teardown boundary, and current basis and validation IDs. `LOCAL`, `NON_PRODUCTION`, and `PRODUCTION` describe a design only; they never grant AWS authority. Production requires an isolated non-production predecessor, an Account/Region boundary beginning exactly `ISOLATED: <explicit boundary>`, and criteria beginning exactly `SEPARATE_OWNER_AUTHORIZATION: <explicit evidence>`.
- Complete the six Well-Architected consideration rows in canonical pillar order. Link each concrete consideration, tradeoff, safeguard, evidence maturity, and revisit trigger to current requirement/risk and design IDs. This is a project design consideration review, never an official AWS Well-Architected Review, AWS Well-Architected Tool result, or observed workload claim.
- Dependency acquisition is `DENY_UNDECLARED`. Either retain the exact no-acquisition sentinel or record one tooling-only `DEP-*` for a current `TECH-*` and canonical `PYPI:` package/version, an exact credential-free HTTPS wheel, the no-lockfile-mutation sentinel, a command-bound SHA-256, wheel-only build-hook denial, only the wheel host, an exact SPDX disposition, the exact `python -m pip install --no-deps --only-binary=:all: --no-index` command, and the canonical VERIFY destination. Runtime/development/build additions, source/VCS installs, bulk lock replay, and other ecosystems remain denied until a separate closure contract binds the resolved graph. A local command prefix or tool capability cannot override the policy.

## Validation, diagrams, and Gate B

- Record `Application source disposition` in the construction envelope. Greenfield application work uses exactly `GREENFIELD_APP_ROOT: app/**`; infrastructure-only work uses exactly `NOT_APPLICABLE — INFRASTRUCTURE_ONLY`; brownfield work lists exact preserved roots already present in the Gate A baseline and `PRES-*` contract. Treat it as an Engine-marked technical recommendation in the Gate B Owner Brief, not another routine owner question. A change stales Gate B; return to requirements only for an owner-requirement or preservation conflict.
- Reject greenfield `apps/**` and `src/**` even when `app/**` is also present. Do not create `app/AGENTS.md`; the root and Deliver authorities continue to govern application work.

- Design contract 9 retains the Project diagram contract, application source disposition, dataset implementation mapping, environment/promotion model, six Well-Architected considerations, and dependency acquisition policy. Fresh templates hold honest `NOT_YET_CREATED` diagram slots. New designs require `SYSTEM_CONTEXT`, `PRIMARY_OUTCOME`, and `AWS_IMPLEMENTATION`; multiple or rich journeys require `JOURNEY`, and declared product states require `STATE`. Canonical data, dependency, recovery, brownfield, or migration records may require `DATA_LIFECYCLE`, `FAILURE_RECOVERY`, or `MIGRATION`. Unknown applicability fails toward requiring the view. An exact approved compatible Design 7 retains its previous required views and digest until a material design revision.
- For each applicable new Design-9 project with required `SYSTEM_CONTEXT` and `AWS_IMPLEMENTATION` views, include `dist/architecture/**` in the proposed Gate B allowed repository write set before presenting Gate B. This reserves only the optional local planned-board output; do not ask another owner question, create a third gate, generate the board automatically, or imply AWS authority. An existing approved envelope is never widened silently.
- Replace each required slot with one project-specific Mermaid block at its bound anchor. Section 14 holds the complete top-to-bottom architecture and section 20 holds the concise top-to-bottom AWS implementation map. Node identifiers use canonical record IDs internally while every visible node names the real actor, component, AWS service, data store, boundary, state, or outcome in plain language. Use at most three boundary levels and six restrained semantic styles. Aim for broad views near 12-20 nodes, nodes with no more than three intentional short lines, and relationships with no more than two short lines, then confirm readability in the rendered dark and default review. Never show a canonical ID as the visible label. A State view must use compact canonical state-model cards and exact recorded transitions; never turn a whole state register into oversized comma lists or invent self-loops merely to make a diagram nonempty.
- Connect every relationship from the canonical producer to the canonical receiver. Show each participating service as an explicit hop, such as API Gateway to Lambda to DynamoDB; never route one arrow through a service, connect to a subgraph title or empty boundary, or guess an unknown intermediate. Use solid edges for primary runtime and data flow and dashed edges for trust, telemetry, control, planning, or optional relationships. Reorder groups or move detail to a focused view when correct edges would cross unrelated nodes.
- Bind sorted basis IDs, referenced IDs, normalized nonempty containment groups, and `{from_id, edge_kind, relation, to_id}` tuples. The semantic digest enters the design digest; the LF-normalized presentation-source digest detects display drift. Moving an unchanged Mermaid block preserves both digests. Label, group-name, and declaration-order corrections change only the presentation fingerprint; moving components across containment groups or changing endpoints, edge kinds, or relationships changes design semantics and stales Gate B. Before an optional architecture-board handoff, compare the system and AWS views by exact direction, one unambiguous directed path, controlled relation family, edge kind, and common-node containment; a mismatch returns to `DESIGN-10`. Diagrams never prove implementation, deployment, or authority. Load `diagram-patterns.md` only on demand when a required Design diagram is incomplete or needs a safe presentation repair.
- Keep one canonical block per diagram. The bottom Diagram guide links to those blocks rather than copying them. Before Gate B, render both architecture views and every applicable focused view on dark and default canvases, inspect spacing and scanability, and correct crowding by keeping one owner-to-outcome runtime spine, placing support concerns beside that spine, and grouping external context, cloud or platform, Region or environment, and functional peers rather than shrinking labels or exposing IDs.
- Complete the existing Gate B Harness Profile from the selected `TECH-*`, profile, risk, data classification, identity boundary, public exposure, recovery target, and AWS lane. Each `HARNESS-*` has one exact command or API and VERIFY destination. Use `REQUIRED`, `CONDITIONAL — <trigger>`, or `NOT_APPLICABLE — <technology/risk reason>`; a triggered conditional is required. Do not add a second Harness table or universal scanner.
- The Harness Profile binds the selected design, tests, and the first construction wave.
- If the owner asks which checks are required, answer from the current Harness Profile row by row: name each applicable `HARNESS-*`, its exact command or API, and its canonical VERIFY destination, then state why every omitted layer is conditional or not applicable. Never answer that request with categories alone or invent a command that is absent from the current profile.
- For `NEW_BUILD`, bind exactly one first construction wave to one approved journey, its requirement and acceptance IDs, and one current required end-to-end Harness row. A referenced spike is disposable, attempt-bounded, and ends with one executable local exit check followed by `DISCARD_AND_BUILD_WALKING_SKELETON`; no spike uses an explicit non-applicable record.
- Classify each infrastructure and delivery path as applicable or not applicable from the selected `INFRASTRUCTURE_AS_CODE`, `SECURITY_VALIDATION`, and `DEPLOYMENT_TOOLING` decisions. Applicable rows bind current `TECH-*`, concrete local/static and planning validation, and the canonical VERIFY evidence destination. Never call an authenticated AWS API merely to complete Design.
- Keep every `EX-*` scenario unique, concrete, traceable, and at an approved Harness layer. Every current reference resolves to exactly one example or applicable property record.
- Classify every measurable approved requirement for generated-property testing exactly once. `APPLICABLE` requires concrete generated inputs or states, preconditions, stable oracle, boundaries, layer, selected `TECH-*`, exact command, run bound, replay format, and VERIFY destination; otherwise record `NOT_APPLICABLE` with a concrete reason. A current `PROP-*` remains required evidence until a design-controlled change replaces it.
- Cover syntax/build; type checking when supported; formatting/canonicalization; linting; secret scanning; dependency/SCA; conditional container and IaC/policy scanning; and material license checks. Extended concerns retain their existing rows: accessibility/end-to-end, visual regression/end-to-end, mutation/unit, SAST/static, DAST/security and privacy, and formal/model checking/property. Choosing applicability is procedural review; deterministic validation begins with the recorded row's status, basis, exact command or API, evidence destination, and Gate B scope.
- Semantic Anchors remain optional internal vocabulary, not a Fastlane dependency or public methodology. Use ATAM only for high-risk designs with competing quality attributes and formal inspection only when material. A Nygard-style ADR is optional supporting rationale for a consequential, hard-to-reverse `ARCH-*` or `TECH-*` decision. The PRD remains authoritative: its `Validation` cell may link `ADR-NNNN` to `../adr/NNNN-lowercase-slug.md`, while the ADR binds the current design revision, decision value, basis, PRD section, evidence, and supersession chain. An accepted referenced ADR must be current before Gate B; ADR prose never enters a design digest or grants construction or AWS authority.
- Project every Engine-marked architecture, technology, Harness, security, data, service, reliability, cost, recovery, deployment, testing, and construction decision into the Gate B Technical Owner Brief. Each decision states what it means for the owner, the exact selection and requirement basis, why it was selected, alternatives and rejection reasons, tradeoffs, risks and safeguards, current evidence maturity, an exact canonical source link, and the measurable condition that would reopen it.
- A requested design correction that introduces a product capability, actor, data type, retention obligation, integration, or journey absent from the current requirements is a requirements conflict, not a design-only correction. Do not keep Gate A current: request or apply the requirements-correction path, stale both gates under the existing rules, and return to REQ-10. Only a correction fully inside current requirements may preserve Gate A and stale Gate B alone.
- The brief is a human projection, not a second design. Missing fields or source bindings block Gate B. Put all links and correction instructions before the exact receipt; after receipt-only approval, the first automatic Deliver update repeats the complete architecture, AWS implementation, diagram guide, Gate B, and current task-progress links.

## Challenger and approval

- Run the read-only architecture challenger after the proposal is complete and only for hard-to-reverse, shared-infrastructure, isolation, recovery, material-risk, explicit deep-review, or evaluation triggers. Quick MVP uses none by default; a justified Quick MVP or Standard review gets 10 minutes, and high-risk/deep review gets 45 minutes. Attempt once per exact design revision, check progress at least every 60 seconds, and finish early. Timeout or unavailability invokes the coordinator checklist and never becomes owner work.
- The challenger returns unsupported AWS claims, unmet requirements, hard-constraint violations, IAM/isolation/recovery/cost/operations gaps, and rejected-alternative concerns with current IDs. It cannot select, write, approve, authorize, or satisfy AWS evidence. The coordinator evaluates findings and remains the sole writer.
- Gate B requires current Gate A, complete Owner Decision Brief, current diagram and Harness contracts, selected architecture, complete traceability, current material AWS evidence, complete change impact, canonical design/envelope digests, and the exact owner receipt.
- For authenticated lanes, `AWS allowed operations` is the deduplicated maximum union across AWS-10, AWS-20, AWS-30, AWS-40, and AWS-50. Execution uses only the phase-appropriate intersection. A Gate B maximum never authorizes deployment or teardown by itself.


## Exact validation obligations

Design 9 requires complete Requirements 1.6. An unchanged, exactly approved
Design 8 retains its historical digest only with no Design 9 surfaces. A new
design using incomplete old requirements must first complete the missing owner
decisions and refresh Gate A; no migration invents facts or approval.

In Validation check bindings, map each acceptance criterion, INPUT, QAS, and
interface to one or more concrete LOCAL_BUILD checks. One CHECK row covers one
complete obligation. Expected result is the exact AC criterion or compact JSON
array of every canonical source row cell for INPUT, QAS, and interfaces. Keep
sorted unique CHECK IDs, executable exact commands, positive time limits up to
86400 seconds, and `docs/project/VERIFY.md#task-completion-evidence` for LOCAL_BUILD.
IaC checks use `docs/project/VERIFY.md#iac-validation-evidence`; the destination
must match the source row and resolve to exactly one canonical heading in the
already-observed VERIFY record. Correct missing or duplicate sections before
presenting Gate B without inventing results or altering an approved binding.
Tests
must actually assert these outcomes; structural bindings alone do not prove
test quality. Interfaces reference precisely the applicable INPUT IDs.

For applicable IaC paths, Required local/static validation and AWS planning
validation contain JSON arrays of concrete commands. Local checks use
LOCAL_RELEASE; future AWS checks use AWS_READ or AWS_MUTATION and still require
separate exact authority. Only a LOCAL completion target can declare later AWS
planning `NOT_APPLICABLE - <concrete reason>`. IAC-L/A obligation IDs use the
declared path index and command index. Expected result binds path, TECH ID, and
command as compact JSON; the destination must match the IaC row. Never claim a
missing destination when the canonical row already supplies it.

Before Gate B, reconcile every exact command against the construction command
boundary. A declared obligation does not itself authorize execution. Include
limits, interfaces, recovery, current sources, and later AWS needs in the brief.
